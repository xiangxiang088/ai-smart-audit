## 四、发现并修复的缺陷（8 处）

### 1. OCR 任务提交被上游队列满拒绝 → 解析失败
- **文件**：`server/utils/paddleOcrClient.js`
- **现象**：4 份 OCR 资料（1 PDF + 3 PNG）报 `创建OCR任务失败(HTTP 400)`
- **根因**：上游 AI Studio 共享队列随机返回业务码 `10010 任务提交队列已满`；原代码把所有业务错误码一律当**永久失败**处理，不做重试。更隐蔽的是 `throwApiError(res, action)` 接收的是**已被读取过的 Response 对象**，二次读体拿不到内容，真实原因被吞掉，对外只剩 HTTP 400。
- **修复**：新增 `readBody` / `makeApiError` 统一单次读取响应体；`createJob` 与 `getJob` 增加**指数退避重试**（可重试业务码 `10010/10011/12001`，可重试 HTTP `429/500/502/503/504`，最多 8 次带抖动）。
- **验证**：`server/scripts/test-ocr-retry.js` 覆盖 recover / exhaust 两场景全通过；生产日志实证"第 3 次尝试成功"。

### 2. 对话接口越权漏洞（安全）
- **文件**：`server/routes/audit/chat.js`（5 处）
- **现象**：普通用户可访问他人项目的审计会话
- **根因**：`auth.isAdmin(req)` —— `isAdmin` 是 async 函数返回 **Promise（恒为 truthy）**，导致 `if (!isAdmin && 归属校验)` 整段被跳过。
- **修复**：5 处改为 `await auth.isAdmin(req.userId)`。

### 3. 前端把 403 当"登录过期"强制登出（连带缺陷）
- **文件**：`public/js/common.js`（PC 端与移动端共用）
- **现象**：后端一旦返回 403（`仅管理员可操作`），前端清空 token 并跳登录页、提示"登录已过期"。用户会误以为被登出，**重新登录后依旧失败**（根因是权限，不是登录态），且丢失当前页面上下文。
- **根因**：`if (res.status === 401 || res.status === 403)` 把两种语义合并处理。
- **修复**：拆分语义 —— **401**（未登录/过期）→ 清凭证跳登录；**403**（已登录但无权）→ **保留登录态**，仅提示后端返回的"无权访问"文案，并标记 `_forbidden` 供调用方区分。
- **说明**：该缺陷在缺陷 2 修复后**才会真正暴露**（此前越权路径不产生 403），故一并修复。

### 4. 疑点台账恒为空（功能缺失）
- **新增**：`server/utils/audit/check/findingScan.js`、`server/routes/audit/findings.js`；**重写** `pc/js/pc-audit-findings.js`、`pc/audit-findings.html`
- **现象**：`audit_finding` 表已建好，但**全项目无任何代码写入**，页面永远空白。
- **修复**：
  - 规则扫描器 5 条规则：量差异常、签章缺失、整数金额、发票连号、签证集中；
  - REST 路由：`GET /`（列表）、`POST /scan`（重扫）、`PATCH /:id/status`（人工复核）、`DELETE /:id`；
  - 前端：风险分级筛选、状态筛选、人工标记误报、一键溯源原件；
  - 核对程序执行后自动刷新疑点台账；`server.js` 挂载路由。

### 5. 勾稽程序右方数据恒为 0
- **文件**：`server/utils/audit/check/boqCheck.js`
- **根因**：右方表名匹配词写死 `%分部分项工程量清单与计价%`，而真实结算表名为**"分部分项工程结算表"**，永远匹配不上。
- **修复**：放宽为 `%分部分项%` 且同时含 `%计价%` / `%结算%` / `%清单%` 之一。

### 6. "无法确认"三态未实现，一侧缺数据被硬判差异
- **文件**：`server/utils/audit/check/boqCheck.js`
- **现象**：`unconfirmed` 计数器初始化后从未赋值，任一侧无数据时直接判 `diff`，虚增差异数。
- **修复**：引入 `comparable = left.length > 0 && right.length > 0`，一侧提取 0 项时 conclusion 置为 `unconfirmed`。

### 7. 处理中状态"僵尸锁"导致解析永久卡死
- **文件**：`server/routes/audit/documents.js`
- **现象**：服务重启后 `parse_status` 永久停留 `processing`，重试接口返回 409，**任何操作都救不回该文档**。
- **修复**：新增 `STALE_PROCESSING_MS = 15 min` 与 `isStaleProcessing(doc)`；`/parse` 与 `/parse-batch` 遇到超时的 processing 允许重新入队，响应携带 `{ recovered }`。

### 8. 导出未包含疑点台账的风险分级与复核状态
- **文件**：`server/utils/audit/check/exportChecks.js`（重写）
- **修复**：疑点台账 sheet 优先取 `audit_finding`（含风险等级 / 复核状态 / 类型）；汇总 sheet 增加"高风险 / 量差 / 待核实"计数公式。

## 五、遗留风险与建议

### ⚠️ 重要：本次勾稽差异数（125 条）不代表系统判错
样本存在**项目错配**：Excel 清单属于「**郎溪县公安局基础管控中心改造项目**」，而结算审核书属于「**东莞市凤岗镇竹尾田综合市场升级改造项目**」——两者是**不同项目**，清单编码自然大面积不重叠，因此产生 125 条"左方（Excel 清单）未见该编码"的差异。

这是**测试样本局限，不是系统缺陷**（修复缺陷 5、6 后程序行为正确）。**用真实生产数据（同一项目的清单 + 结算）复测时，此口径才具备审计意义。**

### 其他
1. **发票连号规则尚未被样本触发**：规则要求 ≥2 张同发票代码的连号发票；当前样本仅 1 张，`high` 级疑点为 0。规则本身有两道保护（`docs.length < 2`、`recs.length < 2` 直接返回）**不会误报**，但**命中逻辑缺真实样本验证**。建议补 2 张以上连号发票。
2. **配置加载隐患**：服务实际加载 `.env`（未设 `NODE_ENV`），而 `ARK_MODEL` 等键仅在 `.env.development` 中定义，目前依赖代码默认值兜底。建议核对两文件键值一致性，避免部署环境串配置。
3. **OCR 空白页**：结算审核书 36 页中 1 页 markdown 为空（封面 / 纯图页），属 OCR 正常表现；如需该页文字需人工补录。
4. **建议后续覆盖**：多张连号发票、同一项目的清单+结算配对、更多签证单以验证"签证集中"规则。
