# 工程审计主流程测试资料包

> **用途**：为「工程审计」主流程（上传 → 解析 → 标注 → 核对 → 疑点 → 问答 → 导出）提供**两个内部自洽的完整项目**，让你可以自己动手把整条链路跑通。
>
> 与 `docs/bid-clearing-samples/`（清标分析专用）分工不同：那边测「1 份控制价 + N 家投标」的横向比价，这边测**单项目内多份资料的纵向勾稽**。
>
> 整理时间：2026-09-23　｜　资料包未纳入版本库（`.gitignore`）

---

## 一、为什么要有这一套

既有的 `docs/samples/06-projects-001/` 有一个**结构性缺陷**：Excel 工程量清单来自**安徽郎溪**、结算审核书来自**广东东莞**——**两份资料分属不同项目**。结果是「清单↔结算勾稽」这条核心链路跑不出真实结论，只能得到一堆「左方未见该编码」的假差异，系统也只能退化成「无法确认」。

本资料包解决的就是这件事：**每个项目内的清单与结算，来自同一个虚构但完全自洽的工程**，项目编码逐条对得上，勾稽能算出真实的匹配数、差异数与核减金额。

## 二、两个项目的定位

| | **项目 A** | **项目 B** |
|---|---|---|
| 目录 | `项目A-房建装修（资料规范）/` | `项目B-市政道路（埋考点）/` |
| 工程类型 | 房建装饰装修 | 市政道路 |
| 定位 | **干净的基线**——资料规范、勾稽基本全绿、疑点以低危为主 | **问题样本**——勾稽有明显差异、疑点密集 |
| 用途 | 验证「系统不会乱报」 | 验证「系统能检出问题」 |
| 资料份数 | 6 份（覆盖全部 6 类自动归类） | 7 份（含 2 张连号发票） |

两个项目配合使用：A 告诉你链路是通的，B 告诉你检出能力是在的。

## 五、为什么资料要这么造（技术约束）

这几条是**服务端代码决定的硬约束**，改造资料时必须遵守，否则链路会静默失效：

| 约束 | 出处 | 说明 |
|---|---|---|
| 清单必须是 **Excel**，且 sheet 名含 **「分部分项」** | `boqCheck.js` 左方查询 | `sheet_name LIKE '%分部分项%'` |
| 结算必须是 **PDF/图片**，且表格 `anchor_label` 含「分部分项」+（计价/结算/清单） | `boqCheck.js` 右方查询 | Excel 走 `sheet_name`、PDF 走 `anchor_label`，两条路不同 |
| 结算 PDF 中「分部分项工程量清单与计价表」必须是**该页第一个居中标题** | `paddleOcrClient.js` | `anchorLabel = 第N页·表格·<该页第一个 title 的前 20 字>` |
| 分部分项表的**每一页都必须单独断页**（含第 1 页） | 生成器 `boqPagesHtml` | 断页缺失时该页表格会与前文粘在同页，`anchor_label` 会**继承前一节的标题**（如「建设工程造价审定表」），boqCheck 右方从此查不到它——**静默失效，不报错** |
| 表头必须是 **序号｜项目编码｜项目名称｜计量单位｜工程量｜综合单价｜合价** | `tableUtils.locateColumns` | 表头须在**前 9 行内**；列名靠关键词正则识别 |
| 项目编码必须能被 `/\d{9,13}/` 命中 | `boqCheck.js` | 公路工程的 `101-1-a` 式子目号**不识别** |
| 归类靠**文件名正则**：合同→contract、签证→visa、清单→boq、结算/审核→settlement、发票→invoice、.png→photo | `documents.js inferBizCategory` | **顺序敏感**：先判「清单」后判「结算」，故结算文件名不可含「清单」 |

> 本资料包的 PDF 由 HTML 经 Chrome 无头渲染生成（`--print-to-pdf`），是**带文字层的清晰 PDF**，不含扫描噪点——目的是测主流程，不是测 OCR 鲁棒性。想压测 OCR，可另用 `docs/samples/扩展素材（可选）/` 里的 86 页扫描合同。

## 六、怎么用

### 6.1 一键质检（上传前先跑）

```bash
cd server
node scripts/verify-audit-packs.mjs          # 校验清单 xlsx 的表结构与列识别（秒级）
node scripts/verify-audit-packs.mjs --ocr    # 追加：把结算 PDF 送真实 OCR，并核对两侧编码对齐
node scripts/verify-audit-packs.mjs --ocr --pack=B   # 只跑某一个项目
```

会输出：清单 sheet 是否命中、六列是否都能识别、提取到的清单项数与合价合计；OCR 模式下还会打印结算 PDF 表格的 `anchor_label` 与两侧编码的 match / diff 预期。

### 6.2 手工走主流程

1. 「📁 审计项目」→ 新建项目（建议命名 `自测A-房建装修` / `自测B-市政道路`）；
2. 进入「📄 资料舱」，把某个项目目录下的 `01`～`07` **全部拖入**，等待解析完成；
   - 检查 6 类自动归类是否正确（清单/结算/合同/签证/发票/照片）
   - 项目 B 的结算 PDF 有 5 页，解析比清单慢，属正常
3. 「✅ 核对程序」→ 依次运行 **▶ 清单↔结算勾稽**、**▶ 三方签章核对**，对照 §3.3 / §4.4 的预期表；
4. 「⚠️ 疑点台账」→ **↻ 重新扫描**，核对命中的疑点类型；
5. 「💬 智能问答」→ 按上面列出的问题清单提问，重点看**反问**是否老老实实答「未在已提供资料中发现」；
6. 「⚠️ 疑点台账」→ 导出 Excel 台账 / Word 发现清单。

### 6.3 建议顺序

```
项目A（先跑）→ 确认链路通、勾稽能算出真实匹配与差异
项目B（后跑）→ 确认各类异常都能被检出
```

## 七、注意事项

1. **数据真实性**：清单部分的编码、名称、工程量取自政府公开招标文件，含真实项目与单位名称；其余配套资料为**按真实结构测算生成**。请仅在测试环境使用。
2. **金额为演示值**：结算书、合同、发票中的金额为构造值，不具备任何结算效力。
3. **重跑即覆盖**：核对程序与疑点扫描均为「同项目同类型软删旧记录后重建」，可放心反复运行。
4. **生成脚本**：`server/scripts/gen-audit-packs.mjs`（确定性，可复现）；校验脚本 `server/scripts/verify-audit-packs.mjs`。
