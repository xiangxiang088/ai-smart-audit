# 清标分析测试报告

**测试日期**：2026-09-22
**测试对象**：清标分析功能（1 份招标控制价 + N 家投标方报价文件）
**测试样本**：`docs/bid-clearing-samples/`（3 组）
**测试方式**：端到端（上传 → 解析 → 建投标方 → 挂接 → 分析 → 校验报告）+ 考点级断言比对

---

## 一、结论摘要

| 维度 | 结论 |
|---|---|
| 功能链路 | ✅ 可用。上传、解析、挂接、分析、出报告全流程打通 |
| 修复的问题 | **4 项**（含 1 项导致报告漏检的核心缺陷） |
| 样本通过情况 | 3/3 组均 `done` 并产出报告 |
| 报告准确性 | 修复后第 1 组考点命中率 **5/9 → 8/9**，反向断言 **2 → 0** |
| 遗留问题 | 1 项（长清单输入被截断，需架构决策，见第六节） |

**最重要的一条**：清标报告此前"漏检严重、甚至给出与事实相反的结论"，**根因不是模型能力，而是非流式长请求被网络中间设备在 ~307 秒掐断**，导致每次都降级到能力最弱的备用模型。改用**流式**后主模型可稳定跑满 894 秒完成分析，报告质量显著回升。

## 四、发现的问题与修复

### P0-1 · 清标资料上传报「project_id 不能为空」

**现象**：上传资料即报错（提示文案在代码里**完全搜不到**）。
**根因**：不是代码抛的，是 **MySQL 列约束错误**被前端透出。清标解绑项目的迁移脚本**只改了 `audit_bid_session`，漏了 `audit_document` 与 `audit_element`**：

| 表 | 何时写 NULL | 漏改后果 |
|---|---|---|
| `audit_document` | 上传资料 | **上传报 `Column 'project_id' cannot be null`** |
| `audit_element` | 解析写要素 | **解析 1 秒内全部失败** |

**修复**：迁移脚本补齐两张表的 `MODIFY COLUMN project_id bigint UNSIGNED DEFAULT NULL`。
（有意保留 NOT NULL：`audit_check_program / audit_check_item / audit_finding / audit_chat_session / audit_chat_message` —— 它们只由项目维度流程写入。）
清标读取解析内容走 `parseService.loadResult(documentId)`（按 document_id 读磁盘），**不依赖 project_id**，故放开列约束即可。

---

### P0-2 · 清标报告漏检（核心缺陷）

**现象**（第 1 组，对照样本包 9 个植入考点）：

| 考点 | 修复前报告表现 |
|---|---|
| 算术错误 `040203004002`（兴业，多计 12%） | ❌ 未检出 |
| 漏报 `050102013001`（扬州一建） | ❌ **反向断言**："未发现漏报项" |
| 工程量擅自改动（双联，改为 88%） | ❌ **反向断言**："工程量完全一致，无擅自改动" |
| 漏项（双联交安缺 1 项） | ❌ **反向断言**："无缺项" |
| 不平衡报价 | ⚠️ 对象写错（应为兴业，写成双联+一建） |
| 汇总与总价不一致 | ⚠️ 数值全对，符号全反 |
| 零报价 `04B017` / 安全文明费偏低 / 暂列金额 360,157.95 | ✅ 命中 |

> **反向断言比漏检更危险**：报告明确写出"无缺项""工程量未改动"，会让评审人主动放弃核查废标线索。

**根因（三层，逐层挖出）**

1. **表层**：报告由**备用弱模型 `lite`** 生成——长清单的逐项核对它做不动。
2. **真因**：服务日志显示主模型与备用 1 **都固定在 307 秒**因 `fetch failed` 失败：
   ```
   [ark] 模型 doubao-seed-evolving        调用失败(307.4s, 可降级)：fetch failed
   [ark] 模型 doubao-seed-2-1-turbo-260628 调用失败(307.3s, 可降级)：fetch failed
   ```
   失败的秒数**卡在同一个固定值**是典型特征：非流式请求在模型长思考期间**一个字节都不下发**，
   被中间网络设备按**空闲超时（~300 秒）掐断**。
   → 完美解释第 3 组（278 s 完成 → 成功）与第 1/2 组（需 > 300 s → **必被掐断 → 降级**）。
   **不是模型能力问题，也不是超时参数问题。**
3. **深层**：`CONTROL_CAP=40000 / PER_DOC_CAP=30000` 把 221 页控制价与 190 项报价**截断**，
   模型看不到完整清单 → 算术/漏项类核对先天做不了。（模型在报告开头**诚实声明了**"其余专业清单未完整展示"，反幻觉表现良好。）

**修复**

1. **流式请求**（核心）：`arkClient.callOnce` 支持 SSE，解析时**每收到一段数据就重置计时器** ——
   语义由"总时长超时"变为**"空闲超时"**，只要模型持续输出就不会被中断。
   默认仍为非流式，**不传 `stream` 行为完全不变**，不影响其它调用方。
2. **超时回调合理值**：单模型 600 s、整链 900 s（此前压到 300 s 反而让主模型更快被误杀）。
3. **降级警示**：若使用了备用模型，在报告正文顶部插入醒目提示，明确"标注未发现异常的检查项均可能不成立"。

### P1 · 测试断言"假阳性"

**现象**：原脚本只查关键词是否出现——报告里出现"漏报"二字就算通过，**哪怕原文写的是"未发现漏报项"**。
**修复**：升级为**考点级断言**：
- `must`：必须出现（如 `040203004002`、`/360,?157\.95/`）；
- `forbid`：不得出现（如 `/工程量[^。\n|]{0,25}(完全一致|无擅自改动)/`），命中即判 `high`（反向断言）；
- 金额统一用容忍千分位的正则，避免 `5,799.95` / `5799.95` 两种写法误判。

用旧报告离线回测：判为「命中 5/9、漏检 2、反向断言 2」，与人工核对一致 ✅

### P2 · 服务僵尸进程（此前遗留）

`server.js` 的 `app.listen` 缺 `error` 监听 → `EADDRINUSE` 冒泡成 `uncaughtException` 被"防崩溃"处理器吞掉 →
进程**既不服务也不退出**，占住端口/日志句柄/DB 连接。已加 `server.on('error')` + `process.exit(1)` 并打印明确中文提示。

## 六、遗留问题与建议

**唯一遗留**：输入被 `CAP` 截断，长清单核不全（第 1 组仍漏检 `040203004002` 算术错误）。

三个候选方案：

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 提高 CAP | 直接调大字符上限 | ⚠️ 受模型上下文窗口限制，盲调有超窗口直接报错的风险 |
| B. 分块调用 | 按单位工程/专业切分，逐块核对后合并 | 可行，但需处理合并与去重，且调用次数与耗时翻倍 |
| **C. 确定性核对下沉到代码** | **算术验算、漏项、零报价、工程量比对、汇总核对本质是纯计算**，代码可做到 100% 准确；LLM 只负责不平衡报价合理性判断、非实质性响应、风险定级与报告撰写 | ✅ **推荐** |

推荐 C 的理由：第 1 组恰好证明——**模型做算术核对会漏**（190 项 × 3 家 = 570 处 `单价 × 数量 = 合价` 验算），
而这类核对在代码里是毫秒级、零遗漏的确定性计算。把"算得准"的部分交给代码、"判得对"的部分交给模型，才是可靠架构。

**待用户确认后实施。**

## 七、复现命令

```bash
cd server
# 第2组（13项，最快）
node scripts/e2e-bid-clearing.mjs --group=2
# 第3组（5家投标方）
node scripts/e2e-bid-clearing.mjs --group=3 --parse-timeout=900
# 第1组（190项，控制价221页PDF走OCR，最慢）
node scripts/e2e-bid-clearing.mjs --group=1 --parse-timeout=1800 --analyze-timeout=1400
```

> 前置：`PaddleOCR-VL`（8080）与后端服务（3003）需在线；`--analyze-timeout` 必须大于服务端单模型超时，
> 否则轮询会先于模型返回而误报"分析超时"。
